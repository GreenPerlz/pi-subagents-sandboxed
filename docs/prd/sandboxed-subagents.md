# PRD: Sandboxed Pi Subagents

## Summary

Add optional Bubblewrap sandboxing to `pi-subagents-sandboxed` so delegated Pi subagents can run with constrained filesystem, environment, and network access while preserving existing subagent orchestration features: single runs, parallel runs, chains, async/status, worktree isolation, and forked/fresh context.

This is the foundation for a later Sandcastle-style workflow: plan issues, run multiple isolated issue workers, review/fix each branch, and merge completed branches with a merge subagent.

## Goals

- Keep `subagent` as the tool/runtime name for drop-in prompt compatibility.
- Keep package identity distinct: `pi-subagents-sandboxed` replaces `pi-subagents`; it is not meant to run alongside it.
- Add sandboxing as optional behavior controlled by settings, per-run params, and per-agent frontmatter.
- Implement Bubblewrap as the first sandbox provider.
- Preserve Pi subagent context semantics:
  - `context: "fresh"` creates isolated child sessions.
  - `context: "fork"` creates branched child session files before launch, then runs children against those files.
- Preserve original host paths inside Bubblewrap for MVP; do not remap to `/workspace` yet.
- Default Bubblewrap network mode to host networking because child Pi processes need model/API access.
- Avoid broad home/secret mounts by default.

## Non-goals for the first release

- No Docker/Podman provider yet.
- No full parallel-issues/Sandcastle workflow yet.
- No domain allowlist networking; Bubblewrap supports `host` or `none` for MVP.
- No `/workspace` path remapping yet.
- No main-agent tool sandboxing yet; first consumer is spawned subagent Pi processes.
- No automatic merge agent yet.

## User-facing API

### Per-run

```ts
subagent({
  agent: "worker",
  task: "Fix the selected issue",
  sandbox: {
    provider: "bubblewrap",
    profile: "host-toolchain",
    network: "host",
    trustProject: true,
    bashWrite: true,
    auth: "env",
    fallback: "fail"
  }
})
```

### Per-agent frontmatter

```yaml
sandboxProvider: bubblewrap
sandboxProfile: host-toolchain
sandboxNetwork: host
sandboxTrustProject: true
sandboxBashWrite: true
sandboxAuth: env
sandboxFallback: fail
```

### Settings

```json
{
  "subagents": {
    "sandbox": {
      "defaultProvider": "bubblewrap",
      "defaultProfile": "host-toolchain",
      "network": "host",
      "auth": "env",
      "trustProject": true,
      "fallback": "fail"
    }
  }
}
```

If no sandbox provider is configured or requested, behavior remains identical to upstream `pi-subagents`.

## Sandbox providers

### `none`

No sandbox. Current upstream behavior.

### `bubblewrap`

Wraps child Pi process invocation with `bwrap`.

MVP profile: `host-toolchain`.

## `host-toolchain` profile

Designed for local developer machines where the host already has the repo toolchain installed.

### Read-only mounts

Mount host toolchain and runtime paths read-only where present:

- `/usr`
- `/bin`
- `/sbin`
- `/lib`
- `/lib64`
- `/etc` or selected `/etc` files needed for DNS/TLS/git
- Pi package/config paths needed to run the child Pi process, excluding secrets by default
- temp prompt files generated by `pi-subagents`

### Writable mounts

- Child worktree when `worktree: true`.
- Child cwd if write inference says writable.
- Child session directory or forked child session file.
- Subagent artifact/progress/status directories.
- Sandbox temp directory.
- Optional package/build caches when configured.

### Network

- Default: `host` network (do not pass `--unshare-net`).
- Optional: `none` network (`--unshare-net`).

### Auth

Default `auth: "env"`:

- Pass only allowed environment variables, e.g. `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GITHUB_TOKEN`, `GITLAB_TOKEN`.
- Do not mount secret directories like `~/.ssh`, `~/.aws`, `~/.gnupg`.

Optional future/auth modes:

- `pi-readonly`: mount selected Pi auth/config files read-only for users relying on Pi OAuth/subscription auth.
- `gh-readonly` / `glab-readonly`: mount selected CLI auth config read-only.

## Writable cwd inference

Sandboxing and worktree isolation solve different problems. Worktree isolation prevents parallel filesystem conflicts; Bubblewrap restricts process access.

Rules:

- `edit` or `write` tools imply cwd/worktree should be writable.
- `bash` alone does not imply cwd/worktree writable.
- `sandboxBashWrite: true` allows `bash` to imply cwd/worktree writable.
- Extra writable paths can be configured for caches/build outputs.

For parallel writable tasks, require or fail/warn unless `worktree: true` is set. For MVP, fail closed for parallel writable sandboxed runs without worktree isolation.

## Forked context behavior

`pi-subagents` already creates forked child session files before launching child Pi processes. The sandbox integration must preserve this:

1. Parent creates forked session file outside the sandbox.
2. Bubblewrap includes that session file path read/write.
3. Child Pi is launched with `--session <forked-session-file>`.

Fresh context behavior uses per-run child session dirs and passes `--session-dir`/session file paths as upstream already does.

## Fallback behavior

If sandboxing is requested and Bubblewrap is unavailable:

- Default: fail closed.
- Optional explicit fallback: `fallback: "none"` may run without sandbox and emit a warning/result marker.

## Implementation notes

Keep sandboxing code internally modular for later extraction:

```text
src/sandbox/
  types.ts
  config.ts
  provider.ts
  bubblewrap.ts
  paths.ts
```

The subagent executor should not hard-code `bwrap` everywhere. It should resolve sandbox config, ask the provider to wrap the invocation, then spawn the wrapped command.

Conceptual seam:

```ts
const invocation = getPiInvocation(args);
const wrapped = sandboxProvider
  ? sandboxProvider.wrapInvocation({ invocation, cwd, mounts, env, policy })
  : invocation;
spawn(wrapped.command, wrapped.args, { cwd: wrapped.cwd, env: wrapped.env });
```

## Acceptance criteria

- Existing non-sandboxed single/parallel/chain tests continue to pass.
- `sandbox: { provider: "bubblewrap" }` launches child Pi via `bwrap`.
- If `bwrap` is missing and fallback is not `none`, run fails clearly.
- Fresh child sessions work inside sandbox.
- Forked child sessions work inside sandbox.
- Parallel sandboxed writable tasks require `worktree: true`.
- Read-only scout/reviewer agents with `bash` do not automatically get cwd write access.
- Agents with `edit`/`write` get writable cwd/worktree as appropriate.
- `sandboxBashWrite: true` allows bash-heavy workers to write.
- Sandbox result output reports provider/profile/network/auth/fallback mode for diagnostics.
